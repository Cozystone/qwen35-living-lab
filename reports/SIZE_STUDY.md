## 최종 결론 (질문: 실패는 모델 크기 때문인가, 구조 때문인가)
1. **둘 다지만 구조 비중이 크다.** 4B→9B 로 키워도 기억이 있을 때의 총점은 두 세계 모두 유의한 차이가 없다(v1 +1.38, v2 +0.50).
2. 크기가 고치는 것: 기억이 없을 때의 대처(v2 FRESH +2.75, 유의), 거짓 완료(v1 LIFE −0.88, 유의), done 을 제때 쓰기, 영수증 폴더 맞히기,
   도구가 '모른다'고 할 때의 정직성(지어냄 15% → 9%).
3. 크기로 안 고쳐지는 것: **반복 고리(9B 가 오히려 많음, 유의)**, 파일 내용 확인 없이 처리(메모까지 이동 30/32), 걸음 소진으로 보고서 미작성.
   → 한 걸음씩 즉흥 선택하는 루프 구조, 계획·점검 단계 부재가 원인. 다음 개선은 모델 교체가 아니라 구조(계획 → 실행 → 점검, 완료 증거, 반복 금지).
4. Heretic(거절 제거)은 3일 세계 성능을 해치지 않았고, 7일 세계의 차이는 조건을 맞추면 유의하지 않다.
5. 방법론: 단일 슬롯도 완전 재현은 안 됨(프롬프트 캐시 재사용 추정). 완전 재현이 필요하면 캐시·MTP 를 끄고 별도로 돌려야 한다.
